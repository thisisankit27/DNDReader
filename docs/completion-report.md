## 2. What was delivered

**Product (v0.1.5, `dist/dndreader_0.1.5-1_amd64.deb`, 326 MB):**

- Open a PDF (picker, `Ctrl+O`, command line); PDFium rendering (pdfrx 2.6.5); scroll, zoom, fit.
- Select text (drag or double-click a word) → pill under the selection / `Ctrl+E` / right-click menu →
  Google results in a right-hand panel (420–480 px); in-panel navigation + Back; "Open in browser".
- Table of contents panel (`Ctrl+T`) with collapsible topics, current branch pre-opened, jump on click.
- Vertical and horizontal scrollbars that stay clear of the open panels; page centres in the free space.
- Editable page-number field (type, Enter to jump), rotate (`Ctrl+R` / `Ctrl+Shift+R`), full screen (`F11`,
  `Esc` leaves), mouse-wheel speed fix, themes (system/light/dark), recents, restored page/zoom/window size.
- Right-click menu: Copy, Find meaning, Select all.
- Selection highlight colour chosen by the user (Menu → Selection colour; sky blue default, yellow, orange, pink,
  grey — Okabe–Ito colour-blind-safe palette), persisted. (v0.1.5)

**Engineering:**

- `lib/` ≈ 4,350 lines, `test/` ≈ 1,700 lines; **115 tests** (unit + widget), `flutter analyze` clean,
  `dart format` clean.
- **Hardened embedded browser:** a public fork `thisisankit27/webview_cef` pinned at
  `0970b4447cb667dc4a512ba5350a39a253d6d273` (CEF 149 / Chromium 149.0.7827.156).
- `.deb` build script, AppArmor profile, sandbox verification script, README rewritten to match reality,
  `docs/implementation-plan.md` and a ~1,000-line `docs/progress.md` with evidence per milestone.

## 4. Security posture (the part most worth scrutiny)

- Dangerous flags removed from the browser command line (fork; **read** from source, and the shipped command
  line was checked in M0b).
- **Sandbox is required and fails closed:** if Chromium's namespace sandbox cannot start the app does not
  initialise CEF and shows "Search unavailable — Open in browser". No SUID `chrome-sandbox` is shipped.
- On Ubuntu ≥ 24.04 the namespace sandbox needs an AppArmor `userns` profile; the `.deb` installs
  `/etc/apparmor.d/dndreader` bound to `/usr/lib/dndreader/dndreader`.
- Cookies/storage are in-memory (empty cache path); nothing is persisted from search.
- **Verified by the owner on the installed package:** `verify-sandbox.sh` →
  `AppArmor label: dndreader (unconfined)`, 3 renderers `seccomp=2`, sharing no user/pid/net namespace with the
  main process, `PASS`.
- **Verified by me:** unconfined launch without the profile fails closed (debug build: no CEF init, no
  renderers, UI state shown); the dev override that disables the sandbox is ignored in release builds (unit test).
- **Known weaker point:** GPU compositing (opt-in, `DNDREADER_GPU=1`) runs the GPU process without its
  seccomp filter (measured), so it is off by default.
- **Maintenance duty created:** shipping Chromium makes security-update cadence this project's job; a bare
  `.deb` has no auto-update channel. Policy (14/30/60-day targets) is recorded in the plan; it is policy, not
  measurement.

## 5. Decisions and why

- **Fix the sandbox, defer navigation vetoing** (owner's call): vetoing navigation is a product choice; removing
  the unsafe flags is not.
- **AppArmor profile, not SUID helper:** the SUID path is being removed upstream; the namespace sandbox worked
  once the process may create a user namespace. AppImage therefore cannot work on Ubuntu ≥ 24.04 (stated).
- **No zero-copy GPU texture:** would need a custom GL texture import in the Flutter Linux embedder; out of scope.
  Measured instead: GPU on gave ~50 % more frames in a scripted scroll, but at the seccomp cost above.
- **Fullscreen via a ~40-line channel in the runner**, not a new plugin (a new dependency was a stop condition).
- **Overlay panels, not reflow:** the document keeps its position when panels open; their widths are fed to the
  viewer as scroll room so nothing is stranded under them.

## 6. What I learned (non-obvious findings that changed the work)

1. **Read the plugin's defaults, not its README.** Security-relevant behaviour (flags, double sandbox-disable,
   shared on-disk profile) was only visible in source; the README's "~330 MB" CEF download was 628 MiB.
2. **Launch context changes sandbox behaviour.** From the VS Code snap shell the process carried a `complain`
   AppArmor label and the sandbox "worked"; launched unconfined it aborted. Evidence from one context would
   have been misleading, so both were tested and the profile was made a deliverable.
3. **`ldd` cannot see runtime `dlopen`.** A clean Ubuntu 26.04 container run found missing `libegl1` and
   `libgles2` that `ldd`-derived `Depends` missed.
4. **Library settings are not always honoured live.** pdfrx applies a changed `boundaryMargin` only on its next
   interaction; re-applying the viewer matrix forces it.
5. **Upstream defaults can be unusable.** Wheel scroll was 0.2× (~10 px/notch on Linux); the default context
   menu was near-invisible in dark theme; double-click was delivered but unhandled.
6. **Focus is a security-adjacent bug source.** The plugin consumed *every* key while its focus node was
   focused, and that node kept focus after the panel closed — hiding Ctrl from Flutter, so Ctrl+wheel zoom
   "sometimes worked". Found by instrumenting the focus chain (14 → 16 and stuck), fixed at both ends.
7. **Widgets that position themselves vs. widgets that are positioned.** A menu returned as a self-positioning
   `Stack` rendered nothing because the library wraps non-positional widgets itself; found by A/B-ing against the
   default menu.
8. **Debounced state is a race with fast users.** The menu consulted state the pill's debounce had not set yet;
   fix is to resolve the value on demand at the moment of the action.
9. **Test the harness's limits explicitly.** The in-app driver injects at Flutter level (OS input does not reach
   the app under XWayland here), polls at 400 ms, and cannot feed the text-input channel; each fix lists which
   parts were therefore covered by unit/widget tests instead.
10. **Accessibility defaults deserve a check, not trust.** The selection highlight was inherited from the theme
    and read as green; making it an explicit, persisted choice from a published colour-blind-safe palette was
    cheap, whereas "fixing" it by picking one new colour silently would have repeated the problem.
11. **Don't regenerate fixtures casually.** Regenerating them changed byte content; only the new fixture got
    the new flags.

## 7. Not verified (honest limits)

- **Real-hardware input:** wheel notch size on the owner's mouse; GTK-level Ctrl delivery (the modifier
  pass-through fix is **read/inferred**, only the focus-return half was observed); touchpad Ctrl+scroll (a pan,
  not zoom — unchanged).
- **Platforms/releases:** `.deb` built against Ubuntu 26.04 library names; 24.04 and others untested; Wayland vs
  X11 of the packaged app beyond an Xvfb start; no lintian, no upgrade-path testing, no apt repository.
- **Fail-closed in the packaged release binary:** observed in the debug build only.
- **Consent wall (EEA/UK):** never observable from this network; behaviour unknown.
- **Scroll feel / GPU preference:** the owner's judgement (M0 check 4), not decided by me.
- **Colour vision:** the highlight palette is the published Okabe–Ito set; it was not run through a
  colour-vision simulator or tried by users, and its look over coloured PDF backgrounds/images was not checked.
- **Gaps:** typed digits into the page field were covered by widget tests, not the running app; triple-click
  not implemented; rotation is not persisted; outline destinations with exact x/y not checked on rotated pages;
  within-page scroll offset is not restored (page and zoom are); `DocumentScrollbars` has no automated test.
- **Not claimed:** Windows, macOS, Android, iOS (plan only).
